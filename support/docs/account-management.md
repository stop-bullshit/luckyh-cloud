# 余额管理

## 使用方式

前端“业务管理 → 余额管理”（`/business/accounts`）进入后直接显示登录用户余额列表。输入用户名搜索，在对应行直接充值、扣减或查看余额明细，不需要先选择用户再查询。充值和扣减按增量调整，不直接覆盖余额。

列表先使用认证用户分页，再一次批量读取本页余额，未开户用户也显示并按余额 0 处理；账户查询失败会显示错误和重试，不把故障误显示为余额 0。

## 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/account/accounts/{userId}` | 查询用户余额；无账户记录时返回 0 |
| GET | `/api/account/accounts/batch?ids=1,2` | 一次查询当前用户页余额；去重保序，最多 100 个正整数 ID，未开户返回 0 |
| POST | `/api/account/accounts/{userId}/recharge` | 充值，正文为正数 `amount`，最多两位小数 |
| POST | `/api/account/accounts/{userId}/deduct` | 管理端扣减，正文为正数 `amount`，最多两位小数 |
| GET | `/api/account/accounts/{userId}/balance-logs?current=1&size=10` | 按最近变动排序查询余额明细 |

业务用户尚未产生账户记录时按余额 0 展示，首次充值时创建账户；已有账户使用数据库单条更新累加并检查 `DECIMAL(18,2)` 上限。充值在本地事务提交时检查 Seata 全局锁，避免购买事务回滚覆盖充值结果。

管理端扣减使用带余额条件的单条更新，账户不存在或余额不足时返回业务状态码 409，不允许余额变成负数。扣减同样在本地事务提交时检查 Seata 全局锁。

登录用户由认证服务维护，余额页面通过 `/api/auth/users` 读取真实 `sys_user` 列表，并通过一次 `/api/account/accounts/batch` 读取余额；账户服务不负责创建用户。购买扣款入口和原有全局事务要求保持不变。

## 余额变动明细（2026-10-04）

先按 [SQL 初始化与升级说明](../sql/README.md) 新增 `luckyh_account.account_balance_log`，再启动更新后的账户服务。此次不改已有余额表，也不根据当前余额猜测过去的充值或扣款；明细从功能启用后的真实变动开始记录。

明细包含充值 `RECHARGE`、管理端扣减 `DEDUCT`、订单扣款 `DEBIT` 和订单退款 `CREDIT`。每条记录返回 `id`、`userId`、`changeType`、`changeAmount`、`beforeBalance`、`afterBalance`、`orderNo`、`transactionId`、`createTime`。增加余额的金额为正，减少余额的金额为负；三个金额字段均为固定两位小数的 JSON 字符串，避免浏览器大金额精度丢失。时间采用无时区 ISO 格式，手工充值或扣减的订单号与事务 ID 可为空。

分页正文沿用 `Result<Page>`，包含 `records`、`total`、`current`、`size`、`pages`；默认第 1 页、每页 10 条，按明细 ID 倒序排列。`current` 必须至少为 1，`size` 必须在 1–100 范围内，非法分页返回 HTTP 400 / 业务码 400。用户无明细时返回空分页，读取不创建账户。

余额更新与明细写入在原有同一本地事务中完成，明细写入失败会回滚余额。账户行锁保证记录的前后余额对应本次实际变动。充值溢出导致余额未变动时不会新增假明细，保留原 JDBC FOUND_ROWS 下的响应行为。Seata 订单扣款和退款将余额、明细同时纳入 AT 分支，全局回滚后对应明细也撤销；全局事务结束前可能暂时读取到一阶段提交的数据，不能把接口返回代替最终协调结果。

订单购买、支付和退款现在传入可选 `orderNo`，便于定位资金对应订单；旧 `/accounts/debit`、`/accounts/credit` 请求只传 `userId` 和 `amount` 仍可用。Java 与 Go 使用相同明细表和查询字段；Go TCC 在 Confirm 时才记录成功明细，Cancel 不产生退款或扣款明细。

### 手工验证

1. 在隔离测试库准备明细表，查询当前余额与明细总数，分别充值、扣减 0.01 元；核对金额正负、前后余额及新增两条记录。
2. 验证余额不足扣减、充值溢出和无实际余额变化场景没有新增明细。
3. 完成订单购买或支付、整单退款，核对 `orderNo`、交易 ID、资金变动与订单状态。
4. 触发购买全写后 Seata 回滚，以及账户退款完成后库存返还失败；等待协调器最终完成，再核对余额恢复且没有残留该事务明细。
5. 并发充值同一账户，核对每条记录的前后余额连续；查询空页、第二页以及非法页大小，核对排序和分页协议。

以上涉及真实数据的步骤由操作者在隔离环境执行，本次源码变更不会自动执行 SQL 或调用写接口。

`AccountBalanceLogMySQLTest` 提供可选真实 MySQL 验证：仅当 `ALLOW_ISOLATED_INTEGRATION=1` 且设置 `ISOLATED_ACCOUNT_JDBC_URL`、`ISOLATED_ACCOUNT_JDBC_USER`、`ISOLATED_ACCOUNT_JDBC_PASSWORD` 时运行，数据库名必须匹配 `luckyh_go_test_*`，默认跳过。操作者应单独创建唯一测试库并准备余额及明细表，测试后只清理该库。该测试验证真实 Mapper、充值/扣减的金额链、无变动不产生明细，以及明细异常时真实 Spring 本地事务回滚；它不启动或证明 Seata AT 全局协调行为。
